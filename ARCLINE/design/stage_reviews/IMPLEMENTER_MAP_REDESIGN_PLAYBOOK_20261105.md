## A. 今回の問題と、修正の目的

これまでの手直しは、窓を広げる、障害物を小さくする、地形の頂点を増やす、反射や風を配置するなど、局所修正を主とした。その結果、マップの見た目は変わっても、プレイヤーの判断は「高所へ行って撃つ」「低所へ行って撃つ」「窓を壊して撃つ」に収束し、独創性と攻略意図が十分に育たなかった。

特に**65面以降**は直線的な地盤・規格化された浮島・四角い部品が目立つ。各面にF/V/W/K/M/T/Bなどのギミックがあっても、ギミックがなければ攻略できない、あるいは有利な戦術が変わる、という因果関係が弱い面がある。「ギミックが置いてある」と「ギミックに攻略上の役割がある」は違う。

**最終目標：** プレイヤーがその面特有の地形を読み、攻防の選択を行い、位置取り・ギミック・破壊のいずれかを意味のある方法で利用できる。画面・実物理・実戦で成立する品質を最優先する。地形の美しさだけ、静的な射線だけ、単発の初回命中だけの合格は不可。

| 固有の攻略コンセプトを提案 | **具体案を起こす。Rは異なる骨格案2つ以上を比較** | 既存面との差別化・戦術意図・抜け漏れをレビュー | 方針承認 |
| 地形とオブジェクトの設計 | **責任者。既存配置を無理に残さず、必要なら新規作図** | 射点・足場・通行・遮蔽・個別部品への指摘 | 完成案を確認 |

| ギミックの調整 | **既存仕様と実効果に沿う配置。物理・状態遷移を検査** | 効果が攻略に必要か判定 | 新ルール変更時に確認 |

| 1面の受入れ資料提出 | **全図・操作ログ・比較表・未解決の一覧を揃える** | 完了基準に達しているか判定 | **その面を承認してから次へ** |

**任せる部分は任せる：** このレビュー文書に記載する形状案は「何を成立させるか」というデザインブリーフであり、厳密なx/y値ではない。地形ポリゴン、曲率、開口幅、部品数、味方・敵の位置、ギミックの細かな座標、攻撃テストの角度・出力は、**実エンジンを操作できる実装担当が自分で決め、実証する**。レビュー担当の指示した仮の座標を無批判に採用しない。

**変更の権限：** ステージの既存物理、キャラクター性能、敵・ボス能力、行動上限、HP、特別ステージのルールは勝手に変更しない。マップ改修だけでは成立しないなら、まずその事実をエビデンス付きで報告し、ルール変更はユーザーが判断する。新ギミックの実装を勝手に増やさず、既存の操作で実現できる解を優先。

## C. 修正レベルを面ごとに明示する

- **R：コンセプトから全面再設計。** 現行マップのポリゴン・島の位置を**出発点にしない**。既存面は「何が失敗したか」「敵・ギミックの既存仕様」の参照資料に限定。世界観、出現敵、既存の技やルールなど必要条件は残し、**地形の骨格・敵味方の配置・攻略経路を新規提案**。最初に別骨格の2案を見せ、なぜこちらが独創的かを説明。採用前に隣接面・同テーマ面との類似性を比較。
- **S：大幅構造改修。** 良い核やユニークな装置は保持できる。ただし大きな地形や主要部品の作り直しを制限しない。「元の島を少しずらしただけ」では不可。改修箇所より攻略上の変化を証明する。
- **K：保持・局所改修。** 独自性と実戦に意味がある核を基本保護。射線・移動・必要な安全性の調整を優先。Rと同じ品質ゲートを通す。Kだから自動合格ではない。
- **K/S：原則K。** 実テストで核が攻略を支えていない場合はSへ変更。理由を記録。

**R/S/Kは初期判定で固定契約ではない。** エンジン検証で課題が判明したら変更してよい。ただし変更前後の狙い、代替案、採用理由は明示。詳細な面別ブリーフは別紙 `STAGE_051_099_REDESIGN_BRIEFS_20261105.md`。

## D. 1面ずつの制作工程（同時並行の多数面生成を禁止）

### Gate 0｜現行状況の確定
- 対象1面のPR#74最新JSON、**実行中のマップ定義**、既存エンジンの表示・座標変換・衝突・物理を読んで、差を確認する。PRの設計JSONが現行実装と同じとは思い込まない。
- 実際にゲームを起動し、ステージ全域とすべての足場・オブジェクト・ギミック・自機・敵・壊せる片を表示する。画面外に出る要素がないか確認する。
- PR#74の旧入力ログ・試作ブランチのログは**旧形状に対する参考値**のみ。修正後の成功判定には使わない。
- **提出：** 現行のエンジン画面、設計座標の出典、重大な不整合リスト。

### Gate 1｜その面の「面白さ」を先に設計
- 最初に「この面でプレイヤーが見つけることは何か」を**一文**で書く。
- 主攻略の行動の流れ、別の判断を成立させる理由、敵位置・反撃・被弾の違いを説明。「高い射点か低い射点か」だけは不足。
- ギミックごとに **なぜそこにあるか／削除すると攻略がどう変わるか／使うルートと使わないルートの差** を記述。不要な装置は減らす方を優先。
- Rは**現行形状をトレースしない別骨格を2案以上**描き、過去4〜5面・隣接面と重複しないことを比較。Sも「既存形状を使い回す必要があるか」を自問。
- **提出：** 1面企画カード（固有テーマ、必須の戦術判断、残す仕様、2案比較または既存核の保存理由）。
- **Gate 1不合格：** 「単に中央島を曲げる」「障害物を増やす」「ギミックを3つ置く」以外の攻略上の違いが示せない。

### Gate 2｜ゲーム表示に一致する形で初稿を作成
- 実装担当がエンジンに適合する座標・ポリゴン・支持面を作成。**レンダラ独自のSVGを唯一の証拠としない**。
- 同じ実ゲームの描画ルーチン・座標変換・カメラ枠で**旧／新を同縮尺**で表示。全体図と重要部分の拡大図を用意。
- 自機・敵の支持面、固体・破壊可能ブロックの実際の衝突境界、ギミックの効果範囲、IDをオーバーレイし、**画面からはみ出すもの、重なる不自然な島、宙に浮く支柱、つながって見えるが通れない通路**をなくす。
- 自然地形は非対称な起伏、窪み、段差、崖の肩、浸食痕を取り入れる。ただし**頂点を増やすだけ、同形六角島を量産、人工物を無理に曲げる**のも不可。形状が射線・遮蔽・移動に関係すること。
- **提出：** エンジン画面の修正前後2枚、衝突可視化、全パーツ一覧と意味、座標差分、移動経路がわかる図。
- **Gate 2不合格：** 図が崩れる、エンジン画面ではない、パーツの支持が曖昧、画面外に欠ける、可視形状と衝突形状が一致しない。

### Gate 3｜幾何・移動・転移を確認
- セグメント自己交差、重複、薄い支持体、孤立足場、プレイヤー車体と砲身のめり込みを検査。**外接矩形上の空隙値だけで通行PASSにしない**。
- 実プレイヤーの当たり判定と実移動量で、P0→候補射点までの**入力列を新座標上で実行**。歩行、段差、落下、転移弾の飛行、着地補正、転移後の向きを記録。
- 各ルートの**到達できる射点**と到達できない理由を明示。仮想射点をテスト開始位置に直接配置して合格にしない。
- 破壊片Dは独立の部品IDで記載し、壊れた片と残った固定支持体を実表示で確認。破壊前・1片破壊後・全破壊後の図を残す。
- **提出：** 全ルートの操作ログと最終着地座標、無効ルートのエラー記録、衝突図。

### Gate 4｜射撃・ギミックの実効果を測る
- **実エンジン**でプレイヤーの車体＋砲身、発射点、風、反射、磁場、雲、噴出、橋の状態と敵コリジョンを含める。
- 少なくとも開始地点P0、主射点、別射点について、複数パワー・複数角度の**命中許容幅**を調べる。命中した1度だけを根拠に「狙いやすい」と書かない。特に射角が狭い場合は具体的に理由を示す。
- 各ギミックについて**実命中弾のイベント履歴**で確認。例：Wならその弾の `bounce`、Fならその弾の風作用、Mなら磁場、Cなら雲の通過。準備弾に作用があるだけでは「最終攻撃に効いた」とは呼ばない。
- P0だけで簡単に倒せる場合、移動先で **被弾が減る／狙える部位が増える／移動敵に追従できる／射角が広がる／消費手数が減る** のいずれかを定量比較。優位がなければ地形を再設計。
- **提出：** 発射位置・角度・パワー・敵位置・ギミックイベント・ダメージ・破壊片のログ。成功例だけでなく失敗例も示す。

### Gate 5｜実戦・上限・AIの検査
- **敵の反撃と既存徒歩移動を含めた戦闘**を実行し、記録した入力列で完走できること。行動上限（面ごとの既存値）と敵HPを満たす。
- 71〜99面は敵の**自律テレポートを含めた実戦検査**が必要。AI未実装なら「マップの静的設計は暫定」「最終戦闘合格は保留」と明示し、実装したふりをしない。
- ボス面は部位ごとの射撃角と敵の攻撃を検証し、1部位への命中だけで勝利可能と判定しない。
- 代表的な複数の初期条件・seedを試し、偶然の1勝や単発弾道の成功だけを合格根拠にしない。どの条件を何回試したか記録。
- 破壊が必須の面では、破壊手数を含めてもクリア可能で、**破壊を強制する意味がある**こと。壊さなくても上層へ進めるコンセプトの面で、勝手に全窓必須へ戻さない。
- **提出：** 各経路の行動／上限、HP推移、敵の位置変化、勝敗、攻撃イベントと再現seed。

### Gate 6｜横断比較・レビュー・承認
- 攻略コンセプトが隣の面や同テーマの面と重複していないか比較。地形、移動、敵位置、ギミック、実戦のうち何が違うか明示する。
- 面の品質を**スクリーンショットと実プレイ証跡**でレビュー担当が確認し、課題を返す。**レビューだけで重要な射撃ルートが未検証なら合格にしない**。
- **1面をユーザーに提出して承認を受け、承認済みを変更禁止としてから次の面へ**。途中で問題が出たら、その1面だけ戻して直す。複数面をまとめて後で直さない。
- 設計承認と技術的な最終合格を分けて表示する。未検証を「PASS」に格上げしない。

## E. 品質基準：落としてはいけない項目

| 項目 | 必須の合格根拠 | よくある誤判定 |
|---|---|---|
| 画面とポリゴン | **ゲーム本体と同じ描画・当たり判定**で全域を見せる | 外部SVGが見栄え良く描けたのでOK |
| 地形の品質 | 支持／通行／視線／射撃へ意味がある輪郭 | 頂点を増やしたので自然になった |
| 繰返し防止 | 近接面と攻略判断・構造が明確に違う | 浮島の上下や色を変えただけ |
| 実到達 | 現初期位置から入力再生で到達・接地 | 仮想座標へプレイヤーを置いて試射 |
| 実射線 | 弾の実物理と銃身コリジョン・角度幅 | 点と点の直線が通った |
| ギミックの意味 | 有無で戦術が変化し、命中弾に作用が記録される | 種類が揃っている／準備弾だけ反射 |
| 実戦 | 敵反撃・徒歩・該当AI・手数を含む完走 | 敵固定・反撃なしの1発命中 |
| 破壊 | 個別IDの除去・支持体の保持・手数負担 | 大きな屋根が1発で全部消えてしまう |
| 不確実性 | 未実装・未検証を明確に区別 | 「一部検証済み」を全面合格と記載 |

**数値を無理に固定しない：** 射角許容幅、足場幅、通路クリアランスはゲームの実コリジョン・武器仕様・狙う難易度に合わせて実測し調整する。固定の「80pxあるから安全」「上下140pxなら移動可能」「角度1点でも合格」は禁止。狭い角度を意図する高難度面は、合理的な代替射点や十分な試行余地があることを説明する。

## F. 実装担当へのタスクとしての明確な指示

1. **まず57面の現状確認から再開**。過去に設計意図が承認された57・58面も、試作JSONを移植せず、原本PRの実機表示をレビューする。コンセプトが成立するなら最小限の改修でよい。59面は未承認の設計を参照として扱い、F04下の通行・上からの実射線・支持面を自分で作り直す。続いて60面、61〜64面、65面以降へ順次進む。51〜56面も出荷前に同じゲートで確認する。
2. 1面につき別の差分／コミット／レビュー記録を作り、**他面の座標には触れない**。共通エンジン修正が必要な場合は別PRに分け、影響面のリグレッションを実施。
3. R対象では**旧マップの座標をコピペして「改善後」としない**。骨格案の比較を先に出す。S対象では、コンセプトが旧地形と両立しなければ主要部を新規作図する。
4. **ゲーム表示が崩れた段階でコミットを止める**。比較図のみ先に作り続けない。旧新双方の同縮尺画面と当たり判定を再確認して直す。
5. レビュー担当に任せるのは**ゲームデザイン評価・成果物の受入れ判断**。実装担当が坐標／コード／検証ログを自分で生成し、未確認の機能の実装や破壊独立性を保証する。
6. 実装担当は**この文書の座標や形を盲目的に再現しなくてよい**。再設計の目的をより良く達成する別案があれば選んでよいが、何が改善するかを証拠とともに残す。
7. 1面の提出物は別紙テンプレート `SINGLE_STAGE_ACCEPTANCE_TEMPLATE_20261105.md` を満たすこと。**レビュー対象が1面分すべて揃うまで次へ進まない**。

## G. 作業停止・差し戻し条件

次のいずれかでその面は**不合格／差し戻し**。次面着手を禁止。
- 実際のゲームで見えない・はみ出る・めり込む・支持面が崩れる・移動できない、または前回の比較SVGのように図と座標が不整合。
- 主／別解が実入力では到達できない。静的な見通ししか検証できていない。
- 座標だけで「実弾命中」「16行動攻略可能」を主張する。
- 部品・敵位置・既存の能力を無断で変える。
- ギミックが攻略にほぼ関与しない／他面と同じ判断が続くのに説明も改善もない。
- 71面以降で自律テレポートAIが未実装なのに、実戦を最終合格と記載する。
- R対象で旧ポリゴンをずらしただけの提案。
- 意図的に狭い射角の理由、代替案、実射撃条件がない。
- **成果物に実ゲーム画面とログがない。**

## H. 成果物と証拠の扱い

各面は最低限 `stage_<NNN>_design_brief.md`、`stage_<NNN>_before_after_<engine>.png`（同縮尺）、`stage_<NNN>_collision_overlay.png`、実装座標JSONまたはランタイム設定、`stage_<NNN>_input_replay.json`、`stage_<NNN>_ballistic_probe.json`、`stage_<NNN>_combat_probe.json`、`stage_<NNN>_review.md` 相当を提出する。**ファイル名は実装プロジェクトに合わせて変更してよい**。重要なのは証拠の内容と検証環境、revision hash、再実行方法があること。

提示のたびに「1.狙う体験、2.全体マップ、3.主・別解、4.実装差分、5.実測結果、6.未検証、7.承認依頼」を1面分だけまとめる。パーツ数・曲率の数字を先に並べず、**実際にどう遊びが変わったか**を説明する。

**本仕様書とPR#74の設計レビューは実装担当への要求事項であり、過去の試作座標を動作保証するものではない。**
