## 1. 今までの修正の問題

床に起伏・浮島・屋根を追加する手法は、見た目を少し変えても戦闘の開始位置と射線の選択を変えていない。特に現行コンパイラの通常1〜99面の`level.spawn`は`[x,interpolate(bp.floor,x)]`で生成されるため、浮島パーツを追加しても**自機が浮島の上から出現するとは限らない**。100面だけは`finalBattle.maps[*].spawns`で別の座標が指定できる。

### 現行の事実値（形状をコードから集計）

| 評価 | 現行 |
|---|---:|
| 1〜40面：床の高低差3設計単位以下 | 14 / 40 |
| 1〜40面：独立した壁・屋根・浮島が0 | 18 / 40 |
| 41〜99面：床がひと続き（ランタイムfloorSegments 1本） | 47 / 59 |
| 41〜99面：浮島部品がある | 36 / 59 |
| 41〜99面：屋根部品がある | 43 / 59 |
| 41〜99面：自機/敵の初期高低差3未満 | 22 / 59 |

部品数と戦術的な配置を混同しない。**浮島が存在する ≠ 自機が浮島にいる／その島を使わないと攻略が変わる**。屋根が存在する ≠ 洞窟が成立している。床の高低差 ≠ 多層構造の存在。

## 2. 12種類の「地形骨格」＋専用最終戦

地形骨格（地面の接続と重なり方）を最初に決め、次に自機／敵の立ち位置、そのあとに攻撃ルートとテーマのギミックを置く。色替え、背景差し替え、左右反転だけでは別パターンと認めない。

| コード | 地形パターン | 成立条件 | 主な体験 |
|---|---|---|---|
| **A** | 開放地形・丘陵 | 1連続床、低丘または視認可能な緩斜面。遮蔽は主役にしない。 | 距離と射角の基礎、息継ぎ |
| **B** | 非対称段丘 | 左右の高低差を明示し、片側を高台・片側を低地とする。 | 上から撃つ／下から見上げる |
| **C** | 深い谷・峡谷 | 谷底を明確に描き、自機または敵の立ち位置と谷を分ける。 | 谷を越える弧／谷を利用する |
| **D** | 分断した地盤 | 床の連続性を断ち、間の空隙を射撃・転移・中継地点で越す。 | 直進できない地形の攻略 |
| **E** | 屋根・庇の回廊 | 屋根の端と開口が主たる射線制約。固定屋根か破壊可能な一部を分ける。 | 軌道を低く通す／上方から回す |
| **F** | 横穴洞窟 | 床・天井・側壁で囲まれた実際の横穴、入口と出口が見える。 | 洞窟内の射点、低い弾道、外からの回り込み |
| **G** | 複層洞窟・地下迷路 | 上下に独立した2以上のトンネル／広間、遮蔽を伴う縦接続。 | 上下の部屋から別ルートを選ぶ |
| **H** | 単独浮島・孤立棚 | 主役となる高所の独立支持面1つと、別の地表／洞窟。 | 浮島を出撃・目標・中継のいずれかに使う |
| **I** | 浮島群・空中回廊 | 高度の違う浮島を複数持ち、空中の経路が主役。 | 島ごとの射点選び／島同士の射撃 |
| **J** | 上下二重通路・立体交差 | 同じ左右領域に上下の独立通路を重ねて、上下からの攻撃を差別化。 | 上路／下路の選択と反転射線 |
| **K** | 縦坑・塔 | 縦方向の移動・発射が主役。中央に柱、途中に足場。 | 見上げ／落下／中継射点 |
| **L** | 橋・渡り廊下 | 分断した陸地を安全橋・開閉橋・渡り廊下が結ぶ。 | 橋がある／ない時の射線と立ち位置 |
| **X** | 最終戦の複合4戦場 | 100面専用の既存4戦場。各戦場は別の骨格と出撃位置を持つ。 | 10機リレーに固有の場面転換 |

**パターンの判定は主構造で1面につき原則1つ。** サブ構造は任意2つまで。ただし「複層洞窟Gと浮島I」などの混在が主目的の100面だけX（複合）とする。実戦の弾道と支持面が存在しない装飾は主パターンにカウントしない。

## 3. 自機と敵の位置の独立設計

地形パターンの文字とは独立して、出撃面は以下の支持種別で記録する。

- `G`：地面、`U`：上段、`L`：下段、`C`：洞窟内、`I`：実際の浮島上、`A`：空中の敵、`M`：100面固有の機体別位置。
- `I/G` は「自機が浮島、敵が地上」、`G/I` は「自機地上、敵が浮島」、`I/I` は「両者が別の浮島」。`C/U` は「自機洞窟内、敵は上段」。
- 3つ以上連続して「地上の自機が右の地上の敵を撃つ」構図は禁止。地面の右上がりと右下がりだけの入れ替えも、独自の体験と数えない。
- 高さの差は設計時の補助尺度。**開始位置が独立した支持面にあるか**、遮蔽と射撃ルートが変わるかを主判定とする。

### 現行実装とのギャップ（実装前に解決する課題）

`build_campaign.py` は通常面の開始高さをメイン床の補間から算出する。上記`I`、一部の`U/C`をそのまま指定するだけでは、浮島や上段への出撃は実現しない。

今後の実装では、独立支持面への出撃を指定する`spawnSurface`（例：`{type:"island", componentId:"...", x:..., y:...}`）等の**宣言的な仕組み**をコンパイラ／初期配置処理に設けるか、既存の安全な地形分割方式で同等の動作を実現する。座標の見かけだけを浮島高さにして車体が落下／埋没する実装は禁止。既存100面の機体別出撃指定との混同も禁止。

必要な実装変更は将来の作業として別途レビューし、今はデータ形式・位置マークの設計だけとする。

## 6. 「同じ形に見える」を防ぐ審査規則

全ての地形案を4つの独立軸で評価する：①**接続構造**（つながった地面／切れた地面／上下二層）、②**出撃支持面**（地面／島／洞窟／高架／飛行）、③**射撃ルート**（直射／回り込み／天井窓／転移／反射／橋の開閉）、④**地形依存の行動**（その場で撃つ／射点移動／部品破壊／切替）。1枚の画像だけで似ている場合も不合格。鏡像や色替えは変化として数えない。

- **同テーマの5面で主骨格4種類以上**。3面連続で同じ主骨格は禁止。
- 序盤10面に最低6種類の骨格を配置。最初の3面には安全な平地／坂の説明を残す。
- 41〜99面で、分断床を**少なくとも24/59面**にすることを設計目標とする（現行12/59）。新しい空隙は転移等を利用した攻略と組み合わせ、詰み経路は禁止。
- 41〜99面で**自機が浮島に初期配置される面を12以上**にする（現行の通常コンパイラでは指定不可なので実装変更が必要）。
- 1〜99面で、洞窟内からの開始を12面以上の候補にする。洞窟内の支持床・射線・見通しが明瞭であること。
- 1〜99面で、敵が浮島に初期配置される面と、双方が別の浮島にいる面をそれぞれ確保する。手前の島が単なる飾りなら失格。
- 地形区分を均等にするためだけに、すべてを難しくしない。単純な爽快面も段階的に配置し、通常面の難度が大ボスと同じにならないようにする。

## 7. ブロックアウト審査の入力項目と承認ゲート

各面につき次の事項がすべて埋まるまで、ステージ座標の大量変更を開始しない。

1. **主骨格コード**・サブ骨格（最大2）・5面中の役割。
2. **プレイヤーと敵の支持面**（島・地面・横穴のどこから出現するか）と出撃座標の検証可能なアンカー。
3. **地面の連続/分断図**・独立支持面・屋根/洞窟の実体・退路。床の高さだけを複雑にして代用しない。
4. **正攻法と別解の2本**（通常弾での成立見込み、有限在庫依存なし）・失敗原因の見え方。
5. **隣の前後2面との構図比較**（シルエット・出撃高度・射線・使用部品）。2軸以上同じなら変更。
6. 100面の確定戦闘と初期状態、1〜99面の既存ステージ導入、章在庫・機体使用制限と矛盾しないこと。

## 9. 追加設計（2026-11-04）：輪郭の形状言語も独立させる

> ユーザー指摘：地面・壁・屋根・浮島が線分と四角形の繰り返しで、マップが直線的すぎる。直線を全廃するのではなく、人工物と自然物の形の差を設計する。

### 9-1. 実データによる原因の確認

現行100面の`floor`は485線分から成り、そのうち274本（約56%）が水平。壁・屋根・浮島は173パーツで、いずれも`poly`の明示指定がなく、`build_campaign.py`で四角形へ展開される。これは輪郭の変化を生みにくい直接の設計上の要因。

エンジンの`geometry.js`は床の折れ線と閉じた多角形`components[*].poly`を処理でき、`build_campaign.py`には`parts[*].poly`を優先する分岐がすでにある。ただし**曲線命令をそのまま衝突形状にする機能はない**。曲線表現は複数頂点の折れ線／多角形の近似で行い、可視輪郭と弾・車体の当たり判定を合わせる。

### 9-2. 12種類の輪郭モチーフ

地形骨格A〜Lとは別に、各面へ輪郭`S0〜S11`を1つ主指定する。テーマと戦術に合う輪郭を選ぶ。同じ地形骨格でも異なる輪郭が使え、輪郭が同じでも自機／敵の位置は独立して変える。

| 輪郭 | 名称 | 形・役割 |
|---|---|---|
| S0 | 整った直線・人工構造 | 水平梁・垂直柱・広い直線甲板・明瞭な角。操作の導入／人工施設を示す意図的な直線 |
| S1 | 緩やかな起伏・丘陵 | 高さの異なる丸い山なりと非対称な小峰。歩行射点に自然な変化を与える |
| S2 | 波食・侵食棚 | 丸いえぐれ・段差・滑らかな海食棚。入射角・水面ギミックとの関係を変える |
| S3 | 断層・破砕稜線 | 高さも幅も不揃いの非対称岩稜、欠けた斜面。高所と低所の射線・遮蔽を変える |
| S4 | 削れた段丘・階段岩 | 長短が異なる平棚と面取りされた段差。位置取りや段差越えの戦術 |
| S5 | 非対称のくぼみ・峡谷 | 緩い側壁と急な側壁を持つ大きな凹地。横断距離・高低差・向きによる射線の違い |
| S6 | アーチ天井・浸食洞 | 高低が変化する弧状天井、大きな入口と細い出口。洞窟内から外への射線・上弧の制約 |
| S7 | 鍾乳・裂け目洞窟 | 天井の割れ目、非対称な岩突起、上下異形の洞内。天井穴の位置を読む、谷と空洞を活用 |
| S8 | 結晶・岩塊の多角形 | 大小の角張った欠片、不等辺台形の浮島。反射・岩角・遮蔽と射角の差別化 |
| S9 | 先細り浮島・風化した孤島 | 丸い／平らな上辺と下へ細る不規則な島の下面。浮島上での出撃・中継・上下射線 |
| S10 | 樹根・有機的な張り出し | 根のような下がり枝、丸みを持つ不規則な庇。庭園・遺跡の自然な遮蔽と空洞 |
| S11 | 曲がった艦体・機械梁 | 折れ曲がった甲板、斜めの肋骨梁、曲面風の船体。人工物でも直方体だけにしない |

**S0は必要な直線。** 橋・人工梁・スタート地点・計測面は意図して直線を使う。ただし、100面すべてを長い水平床＋四角い部品で設計しない。単なるノイズ状のギザギザ、全段を小刻みにずらしただけの地形も失格。

### 9-3. マクロ形状・メゾ形状・接触面の3層で決める

1. **マクロ形状：** 全景で見える大きな起伏。半円状の谷、えぐれた崖、不等辺の岩柱、先細り浮島、巨大アーチなど。画面縮小でも1面ずつ違う形を認識できる。
2. **中規模形状：** 岩の欠け、段丘、斜面の肩、浮島の下面、洞窟の鍾乳部分など。遮蔽・跳弾・低弾道に意味を持たせる。
3. **支持・接触面：** 車体が乗る安全な平棚、砲塔の余裕、跳ね返る壁など。視覚的な自然さより正しい物理・読みやすさを優先する。地形の装飾は当たり判定に存在しない時、描画上も当たるように誤解させない。

### 9-4. 実装可能なブロックアウトの書き方

**地面の丸み：** `floor` の折点を増やして、丸い丘を短い直線の連なりで近似する。例（座標は説明用で未検証）：`[[0,10],[8,10],[15,10.6],[21,12],[27,14],[34,14.5],[41,14],[48,12.5],[55,11],[63,11]]`。平坦な棚と緩やかな曲率を併存させる。全部を同じ間隔で波状に揺らさない。

**角張った／えぐれた浮島：** 従来の`{"kind":"island","x":40,"end":60,"top":25,"thickness":4}`に`poly`を明示し、必要なら`[[40,25],[60,25],[57,20],[51,18],[45,21]]`のような非矩形にする。この輪郭はコンパイラが`components[*].poly`へ渡す。**上辺は車体の支持面、下辺は別の形状**として区別する。

**アーチ・岩洞：** 天井を横長の単一四角形にせず、複数頂点の閉じた輪郭で上部の岩と内部開口を描く。洞窟の床・天井・側壁は複数の実体ポリゴンで組み、空間に偽の塞がりを作らない。湾曲天井は折線近似、壁や床と交差する部分は衝突判定で確認する。

**重要な実装制約：** `floor`は同じxに2つの高さを持つオーバーハングを直接表せない。その場合は`parts[*].poly`か独立支持面を使う。閉ポリゴンは交差・自己交差禁止、床の点列はx昇順。歩行用の斜面は35°以下、出撃地点の支持床は最低幅10設計単位を目安にする。極細トゲ・極小凹凸は近似過程で省き、弾の当たり判定と見た目のずれを避ける。

## 11. 後半の射点開拓を許容する優先改訂（2026-11-04）

> [10面の実測v3設計](reference_maps_10_v3.md)・[座標／射線／移動テスト](reference_maps_10_v3.json)・[初期／歩行後／テレポート後アトラス](reference_maps_10_v3.html)を新しい検証基準とする。**第10節の「初期射線が必須」という文言は、本節を優先して読み替える。** v1/v2の旧試作は履歴であり一括実装しない。

**初期射線を必須にするのは主として導入帯（1〜39面）。** 40〜49面は初期射撃を基本に射点変更の意味を学ぶ。50〜99面では次の3つを意図的に混在させる。

| ラベル | 設計体験 | 必ず検証すること |
|---|---|---|
| `shot-first` 初期射撃 | 直ちに撃てる | 実際の有効打、意味ある別解 |
| `movement-advantage` 射点改善 | 初期でも撃てるが移動後に狙いやすさが増す | 開始・移動後の射線数や許容幅、足元角度の差、実歩行 |
| `movement-first` 射点開拓 | 初期位置では有効射線が乏しいが、移動先で明確に成立 | 移動できる／着地できる／着地後に撃てる／射点が見える／不公平な反撃がない |

**大ボスを一律に射点開拓型にはしない。** 各章で射撃開始のパターンを意図的に変える。今回の具体例は50面の`movement-first`、80面の`movement-advantage`、90面の`shot-first`。

- **50面の設計上の成立例**：x=32の水平棚は初期弾道144/646条件で0件。左へ40px退いて右へ2px向き直すと通常弾4件が成立し、全件で上昇気流Uが作用。テレポート後の追撃が成立する試行も14件。**逆方向の小さな向き直しが不快なら、この座標は不合格**とし、島へのテレポートを主ルートにするか、前進で射点が開く形へ修正する。
- **80面の成立例**：自機の浮島x=20では初期有効打1件、右40pxで6件、右80pxで8件。磁場Mを通る成功弾道が残り、向き反転不要。
- **移動の快適さ**：移動後の精密射撃足場の車体角は原則4°以内、付近40pxの車体角変化は3°以内。急斜面は通過に使ってよいが、精密射点として強制しない。歩行140px/ターンとテレポートの既存規則を守る。
- **ガイド設計**：初期位置で撃てない面には、空いた射撃棚・壁の開口・低い横穴・空中島など、移動先の視覚的手掛かりを設ける。隠し正解の座標探索を攻略と呼ばない。
- **ギミック判定**：初期射撃に作用しなくてもよい。**移動後の成功弾道**で作用するなら意味がある。ただし成功弾道から離れた飾りギミックは失格。
- **敵AI・ターン進行・演出**：地形・物理関数だけの成功をクリア可と呼ばない。移動の最中と後に敵反撃がどう発生するか、実装時に必ず再評価する。
- **100面の例外**：固定10機・4戦場・各HP70／各表示100ダメージ／80行動等の最新契約を維持し、各機体の射撃開始状態を個別に評価する。通常面の開拓基準を機械的に適用しない。

**承認の順序：** まずv3で設計差を確認 → 10面の正式実エンジン／敵AI／ターン行動検証 → 人手の照準・向き直し・理解度の試遊 → 100面の個別ブロックアウト。設計図のGit登録だけではゲーム反映済みと扱わない。

\n## 13. 最優先：敵の攻撃圧に連動した「1面ずつの設計・承認」方式（2026-11-04）

1. **従来の100面一括ブロックアウト・一括自動生成・一括反映を中止。** 主骨格A〜L・輪郭S0〜S11・各面の現在の割当は参考材料であり、確定ではない。**1→2→…→100**の順に、各ステージの断面図と配置・ルート・難易度評価を提示し、ユーザーの確認・了承を受けてから次の面へ進む。

3. **難易度は地形単独では決めない。** 敵プロフィール・照準誤差・ステージ補正・ダメージ補正・敵HP/ボス耐久・AI攻撃型・行動上限・推奨手数と、斜面・遮蔽・移動時間・射点開拓の負担を**別々に評価**して総合判断する。敵性能を勝手に書き換えて地形の過剰難度を帳消しにしない。
4. 現行`engine.enemyParameters`の敵精度誤差／被ダメージ補正：**1〜40面=1.00/1.00、41〜60面=0.90/1.00、61〜80面=0.75/1.05、81〜99面=0.65/1.10、100面=0.70/1.10**。Easy/Normal/Hardの誤差倍率は1.40/1.00/0.65。数字は**命中率ではなく誤差倍率**。41・61・81面で地形難度を自動的に跳ね上げない。
5. **見た目の豊かさは序盤から維持**するが、序盤の攻略判断は1つずつ。後半は初期位置から射線が通らなくても、安全な歩行・転移と分かりやすい中継射点で攻撃できればよい。敵を島・洞窟・逆斜面・崖裏などにも配置する。起伏と足元傾斜は射撃の楽しさとして扱うが、理不尽な極細角度に依存させない。
6. **マップ幅は目的で選ぶ。** v4の1100〜1960pxをすべての面の最低・最高幅として強制しない。距離が広がるなら、敵の反撃・行動制限・カメラ見渡し・移動の猶予も設計図で確認する。
7. **今回の設計工程に自動戦闘シミュレーションは含めない。** 各面の仕様照合と断面図・主経路・別経路・難度の定性レビューを基本とする。コードへ実装する際のテスト・検証は別工程とし、未実施を実施済みと扱わない。

## 14. 学習目標も地形刷新に合わせて個別変更可能（2026-11-04 最新決定）

**既存の学習目標は参考情報であり、新しいマップを旧学習目標に従わせる必要はない。** プレイヤーの体験がより良くなる場合、目標自体を各面ごとに「維持・発展・刷新」する。v4の10面を旧目標に合わせて無条件に弱体化・旧地形へ差し戻すこともしない。

- **変更の単位は1面のみ**。最初のステージの旧目標と、新しい地形に合わせた提案目標、なぜ変えるのか、敵の攻撃精度・ダメージ・手数との整合、前後面に対する学習順序を設計シートに記す。
- **現行難易度仕様は別軸**。敵AI、ダメージ倍率、HP、行動上限、100面の10機固定リレーなど、学習目標の更新だけでゲームの確定ルールを上書きしない。
- **段階的な学習を守る**。浮島や洞窟は序盤でも登場してよいが、どの攻略操作を必須とするかは難易度に応じて決める。初見で理解しやすい難しい地形と、理不尽な難しい操作を混同しない。
- **レビューの流れ**：旧目標（記録として残す）→刷新地形の体験→新目標の提案→変更理由→前後面との関係→ユーザー承認→台帳更新。未承認の学習目標を確定済みとは表現しない。

新しい定義と台帳項目は[個別設計方針](stage_by_stage_map_design_policy_v1.md)と[100面の進行台帳](stage_map_design_register_v1.json)を優先する。
