## 1. 体験目標

敵が障害物に向かって無意味に撃つだけではなく、**自分に有利な射線へ位置を変える**。プレイヤーは、敵の徒歩・テレポートによって変化した射線を読み、地形・遮蔽・既習得ギミックを使って対抗する。

- **既存の短距離の徒歩・微移動は削除しない。** 1〜39面の現行動作は維持し、40面以降も敵が射角を少し整える既存の徒歩を利用できるようにする。そのうえで**40面以降には、地形・遮蔽・弾道から有利な射撃位置を判断して歩く「戦略的な徒歩」を追加する。** 40面は徒歩そのものの初導入ではなく、徒歩の目的・判断力を拡張する境界である。
- 71面以降の通常敵には、**射線を変えるための自律テレポート**を与える。プレイヤーの近くへ突撃する能力ではない。
- 71〜99面を通して**転移先の判断が上手くなる**。単純に後半ほど転移頻度を上げる設計にはしない。
- 敵が**転移しない戦闘も正常**である。転移を見せるためだけに不利な移動をさせない。

## 2. 最重要：転移の回数上限と発動制御【確定設計】

### 2.1 戦闘ごとのハード上限

| 面 | 対象 | 1戦闘での敵転移の最大回数 | 設計目的 |
|---|---|---:|---|
| 1〜70 | 通常敵 | **0回** | 既存射撃・徒歩を維持。新しい自律転移は導入しない |
| 71〜74 / 76〜79 | 通常敵 | **1回** | 射線変更を体験させる。初期の判断の粗さを残す |
| 81〜84 / 86〜89 | 通常敵 | **2回** | 敵が攻防・遮蔽をより考えながら異なる射点を使う |
| 91〜94 / 96〜99 | 通常敵 | **2回** | 回数は増やさず、最大2回をより効果的に使う |
| 75 / 80 / 85 / 90 / 95 | 中ボス・ボス | **0回**（本PR） | 部位と固有攻撃の配置関係を保護 |
| 100 | 専用最終戦 | **0回**（本PR） | 既存4戦場・10機リレーと専用敵挙動を保護 |

**「最大」は発動義務ではない。** 戦闘によって0回、1回、許可された上限内で2回があり得る。敵が賢くなることを転移回数の増加で表現しない。勝手に上限を3回以上へ増やさない。

### 2.2 クールダウン

- **転移した敵は、その後の敵2手番では再転移できない。** 例：敵手番tで転移したら、t+1とt+2は通常射撃または徒歩＋射撃などから選び、最速でもt+3で再評価する。
- クールダウンは実際に有効な敵行動が進んだときに数える。ポーズ・画面遷移・敵スキップ・勝敗確定などを通じて不当に進めない。
- 転移上限・クールダウンは**敵側の戦闘状態**で管理し、演出や描画のフレーム数に依存させない。
- 転移に失敗した場合は**転移回数を消費させない**。合法な行動を選び直すか安全な現状維持・通常射撃にフォールバックする。無限リトライは禁止。

### 2.3 発動条件と確率

- **5・10ターン目などの固定ターンを発動条件にしない。** ターン番号は戦況の説明には使えるが、固定節目トリガーにしない。
- 転移可能回数が残り、クールダウンが終わり、現在の位置より**実際の射線・安全性が改善する候補**がある場合だけ「転移の価値」を評価する。
- 現在地からの射撃や徒歩改善が同等以上なら、転移しなくてよい。候補が合法でも転移が自動確定するわけではない。
- 転移するかどうか、および準最善の候補からどれを選ぶかには**seed付き乱数**を使用できる。発動確率は固定ターンごとの強制抽選ではなく、その時点の相対的な有利さに従う。
- **毎ターン70%で転移する設計は禁止。** かつての「戦闘全体の約70%で少なくとも1回転移」という例は確定値ではない。必要なら実際の試行から戦闘単位の発動割合を測って調整する。
- 最大回数まで転移した後は、敵の残りの行動が常に通常射撃・徒歩などで完結すること。

### 2.4 1手番の処理と公平性

- **転移は敵の1手番を丸ごと使う行動。転移した同一手番では射撃・徒歩・部位攻撃を追加しない。**
- 通常の**徒歩＋射撃**という既存の行動連結は、現行ルール・移動距離・射撃処理を尊重して継続してよい。
- **事前予告は行わない。** ただし転移後に一目で位置変更が分かる視覚・音の演出を与え、次の自機手番で対処できるようにする。
- 同じ敵手番内で複数回転移しない。転移先で直ちにプレイヤーを攻撃しない。

## 3. 徒歩AI：40面以降の位置取り

### 3.0 既存の微移動を残したうえで戦略的徒歩を追加【確定】

- **既存の微移動（短い距離の射角調整）は存続させる。** 現在地での通常攻撃や微調整が有効な場面では、従来の動きを選べるようにする。微移動を無効化して全て大きな戦略的移動に置き換えない。
- **40面以降は戦略的な徒歩を新たな判断候補に加える。** 少し動くだけでは遮蔽・屋根・岩壁を回避できないが、同じ地続きの安全な射点へ移れば実際の射線が開く場合に、より大きく歩いて位置を変える。必ず長距離歩く、毎ターン歩く、という意味ではない。
- **行動の比較：** `その場で射撃 / 既存の微移動＋射撃 / 戦略的徒歩＋射撃` を比較し、71面以降はこれに自律テレポートも加える。微移動と戦略的徒歩を毎手番機械的に連続発動しない。既存の短距離調整は通常の判断候補またはフォールバックとして再利用できる。
- **共通徒歩予算：** 40面以降の1敵手番に実行した微移動と戦略的徒歩の**実移動距離を合算して最大140px**。2種類の徒歩に別々の140pxを与えない。1〜39面の既存挙動・距離制限は改変しない。
- 徒歩の意思決定が微移動の既存処理と衝突し、意図せぬ2回移動・上限越え・複数回射撃を発生させないよう、**行動計画の選択と実行を一元管理する**。

### 3.1 基本判断

1. 現在地の攻撃可能性を確認する。既存の地形物理・弾道の探索を利用する。
2. 現在地が有利なら**歩かず撃つ**選択を許容する。
3. 攻撃しにくければ、同じ地続きの支持面で左右に合法的に歩ける候補を生成する。
4. 各候補で**実際の砲口・弾道・遮蔽・ギミックの作用**を評価し、攻撃可能性、被反撃リスク、歩行負担を比較する。
5. 徒歩の結果が改善しない場合は無理に歩かず、現位置から可能な行動を選ぶ。壁に向かって歩き続ける・進めないのに歩行を繰り返す挙動を防ぐ。

### 3.2 徒歩時の注意

- 敵の移動先は**毎回の地形・戦況から計算**し、固定x座標の巡回ルートにしない。
- 自機との間に歩行だけで越えられない谷・高低差・橋があれば、既存衝突・支持判定を尊重し、ワープのように跨がない。
- 斜面・屋根・足場の関係により、**歩くことで明確に有効射線が増える**ことが重要。既存の `G.move` / `support` / `clearBody` に従う。
- **【必須・確定】ステージ40以降の通常敵の徒歩移動距離は、自機の通常歩行と同じ「1敵手番あたり合計最大140px」に制限する。** 140pxはゲーム座標（実ピクセル）の水平歩行実移動量の絶対値を積算した上限で、既存の微移動＋戦略的徒歩、片道・往復・分割移動の**確定した実移動**を通算する。仮の移動候補や実行前のシミュレーションは移動量へ算入しない。敵のプロフィールや判断能力が上がっても、歩行上限そのものを140pxより増やさない。
- 既存の自機の `movementLimit=140`、`movementRemaining()`、`walkUsed` と同じ基準を敵側にも適用し、敵専用の手番内累積移動量を保持・消費する。**敵の行動選択と移動演出・Worker計算・フォールバックのどの経路からも上限を迂回できない**ようにし、実際に動けた距離だけを計上する。
- **140pxは徒歩の上限であり、テレポートによる位置変更距離には加算しない。** ただしテレポートした敵手番は歩行も射撃も追加しない。自機の移動強化スキルなどの個別効果を敵の通常徒歩に流用しない。
- 既存の敵プロフィール・地形による移動可否、衝突、射線評価は維持するが、敵の徒歩距離に140px未満の個別制約がある場合も、その制約と共通上限の小さい方を守る。
- 40面から敵全員が毎ターン歩くことを義務にしない。既存の微移動を選ぶ場合・戦略的に大きく動く場合・その場で撃つ場合を残し、**40面以降に有効射線を作るための徒歩判断が増える**ことを目標とする。

## 4. 自律テレポート先の生成と安全条件：71〜99面

### 4.1 固定地点の禁止

- **固定されたテレポート先一覧をステージごとに用意しない。** `spec.blink` やプレイヤー専用BLINK位置を、敵の固定候補として流用しない。
- **現在有効な実地形の支持面から着地候補を動的生成**する。床、崖肩、浮島、開いている橋、破壊後に露出した台地など、実ワールドの状態に応じて候補が変わる。
- 支持面の離散サンプリングは許可するが、判定はサンプリング座標への直接配置ではなく、`geometry` 側の実衝突・安定着地判定で行う。
- 相手が移動したり橋や壁が変化したら、**候補の合法性と評価を更新**する。開閉橋や壊れた床の上へ飛ばない。

### 4.2 絶対に守るハード制約

1. **地形へのめり込み・空中停止・橋のない場所への着地なし。** 敵サイズ・足元傾斜・頭上余白・支持の両端と衝突を確認する。
2. **プレイヤーの至近距離へ転移しない。** 初期評価用の距離下限は約300pxを目安にし、世界幅・敵と自機の大きさ・射程に応じて調整する。少なくとも現行の衝突離隔条件より十分大きいことを保証する。水平距離だけでなく実距離と見通しも評価する。
3. **プレイヤーを追跡して近づくことを主目的にしない。** 狙いは別角度からの射撃である。
4. **転移後に全く攻撃できない、または一方的に守られて敵が攻略不能になる位置を恒常的に選ばない。** 初期AIの下手さは相対的に有利でない位置選択として表現し、物理的な破綻として表現しない。
5. 既存のワールド境界、動的な障害物、ボス部位、相互の機体当たり判定を守る。
6. 次の自機手番に対処の余地があること。転移先が一度選ばれたら絶対安全になる地形を使わない。

### 4.3 転移先をどう評価するか

候補ごとに次の観点を評価する。**値そのものは実装時のチューニング対象であり、ここで固定のAIスコア係数を承認しない。**

- 転移後に**有効な射角の許容幅**が増えるか（1点だけの極細弾道を過大評価しない）。
- 現在の実際の地形状態で、敵の使用武器・ギミック効果を通して攻撃できるか。
- 自機から反撃されやすいか、遮蔽があるか、敵も脱出・再移動できるか。
- 転移しなくても**徒歩1回で改善**できるか。徒歩が十分なら転移資源を温存できる。
- 次の敵手番での攻撃機会と、転移の1手番コストを考慮する。
- 現在地に留まる選択も候補に含める。

## 6. 既存ゲームへの実装統合

### 6.1 現行の実装を尊重する

現行コードから確認した役割は次のとおり。

- `game/dist/engine.js` の `enemyMoveTarget(s)` は、現状、同じ支持面での左右徒歩候補を評価する。**既存の短距離徒歩を削除せず、40面以降の戦略的徒歩候補と同じ行動選択器で比較する。** 微移動と戦略的移動の両方が実行されて140pxを超えること、既存徒歩の後に別系統が無条件で追加移動することを禁止する。
- 同じファイルの `cpuPlan(s, random)` は既存の弾道評価と照準誤差を用いて射撃を計画する。
- `game/dist/game.js` の `requestCPU()` と `update()` は、CPUの移動→射撃の演出・状態進行を管理している。
- `game/dist/cpu-worker.js` はWorker側で移動と射撃計画を作る。Workerが使えない場合はメインスレッド側にフォールバックがある。
- `game/dist/geometry.js` には `support`、`clearBody`、`safePosition`、`move`、`teleportLanding` などの物理判定がある。ただし現行の `resolve()` にあるテレポート処理は**自機 (`units[0]`) 専用**なので、そのまま流用して敵を転移させてはならない。
- 既存の `next()`、`boundary()`、`guardian()`、`S_ENEMY_SKIP`、敵照準学習・難易度補正・最終戦固有ルールを保持する。

### 6.2 実装方針

1. **敵行動の意思決定を一箇所に統合**し、例えば `planEnemyAction(state, seededRng)` のように `shoot / walk-then-shoot / teleport` の明確な行動型を返す方式を推奨する。関数名は提案であり既存の実APIではない。
2. 候補生成・評価時には**実ゲーム状態を不用意に変異させない**。仮移動後は位置・向き・足元・世界・RNG状態を完全復元する。Workerとフォールバックで同じ結果を返す。
3. `teleport` を選んだ場合、敵手番は**転移だけ**で解決し、その敵手番では `cpuPlan` による発砲を行わない。転移成功後に上限回数とクールダウンを更新する。
4. 機体の位置変更を既存の自機専用転移から一般化する場合も、**自機側の弾道・着地・所持技・アニメーションを破壊しない**。
5. 転移後の敵の支持面・向き・物理当たり判定を更新し、次の自機ターンの攻撃とマップカメラに即時反映する。転移前後のアニメーションを設けても当たり判定と実位置を不整合にしない。
6. 既存の `cpuMove` と敵射撃・ターン遷移へ組み込む。転移に追加射撃を付けず、敵スキップや勝敗処理が2重実行されないようにする。
7. **戦闘単位の状態**として `teleportCount`、`teleportCooldown`、最後の転移位置等を保持できる形にし、戦闘開始・再挑戦時に正しく初期化する。途中セーブ・復元に対応する場合、欠損する旧セーブでも安全な初期値となるよう互換性を維持する。
8. 敵AIの新しい候補評価が大量の弾道探索を引き起こさないよう、まず支持面・近接距離・遮蔽で候補を減らしてから共通物理評価する。モバイル/Worker無効時の処理時間を計測し、既存の応答性を保つ。
9. `ARCLINE/game/runtime.json` と正式な生成手順を確認し、**生成元／配布物／キャッシュバージョン**を一致させる。`dist` のみの手作業編集を放置しない。

### 6.3 推奨する行動選択の概念フロー

```text
敵の手番が到来
 ├─ 敵スキップ・戦闘終了・固有ボス処理? → 既存処理／終了
 ├─ その場で攻撃した場合を評価
 ├─ 徒歩による射線改善を評価
 ├─ 71〜99の対象通常敵かつ残り転移回数あり、CD=0?
 │    └─ YES: 現在の実地形から合法な遠距離着地点を探索
 │             → 転移後の射線/遮蔽/次手番の価値を評価
 │             → その場・徒歩と比較し、優位性に応じてseed付き抽選
 ├─ 転移が選択された → 敵を転移／回数+1／CD設定／この敵手番終了
 ├─ 徒歩が選択された → 既存ルールで歩行 → 射撃
 └─ それ以外 → 現在地から射撃
```

**重要：** 転移先や発動ターンを固定しないことと、発動上限を設けることは矛盾しない。上限・CDは過剰発動を防ぐハード制約、実際の行動選択は状況評価と乱数に任せる。

## 7. テスト・検証要件

### 7.1 必須の単体テスト

- 1〜39面の既存の短距離徒歩・攻撃頻度・移動距離は比較テストで変化しない。40〜70面（通常敵）では**微移動を残しつつ、戦略的徒歩判断を追加**するが、テレポートは使用しない。
- **40〜99面の通常敵は、既存の微移動と戦略的徒歩の実移動距離の合計が、1敵手番内で常に140px以下**。同一方向への連続移動、往復、途中で障害物にぶつかる場合、Workerとフォールバック、敵が射撃する前後の状態遷移を含めて確認する。既存の自機通常歩行も従来どおり140px以内である。
- 転移を行った敵手番の徒歩移動量は0px。転移距離は140pxの徒歩予算には算入せず、別途転移上限・クールダウンで管理する。
- 71面で合法な好位置があれば転移を選ぶこともある一方、転移0回のシードも成立する。
- 71〜79面の通常敵は、**いかなる戦況・RNGでも転移最大1回**。
- 81〜99面の通常敵は、**いかなる戦況・RNGでも転移最大2回**。
- 転移後の2敵手番で再転移しない。上限に達したら以後どんな候補が現れても転移しない。
- 転移後の同一手番で弾を撃たない。プレイヤーのHPや防御へ敵攻撃ダメージを加えない。
- 固定ターン5・10などでの転移強制がない。敵が有利な場合は現在地に留まる。
- プレイヤーの近く、物理的に危険な空中や壁内、閉じた橋、壊れた床には転移しない。
- 転移候補は実ワールドに応じて変化し、固定x座標のテーブルに依存しない。
- 既存の敵徒歩、プレイヤー徒歩・転移、通常射撃・敵照準誤差、既存中ボス・ボス・100面の専用ルールは退行しない。

### 7.2 必須の結合・再現テスト

- **代表面：** 40、50、60、70（徒歩・ボス既存処理）／71、74、76、79（初期テレポート）／81、86、89（中期）／91、94、97、98、99（後期）／75、80、85、90、95（固有ボス除外）／100（最終戦除外）。
- 各代表面で**未転移・早期転移・後期転移・複数回転移（上限2の場合）**、破壊による地形変化、橋開閉、磁場/風/雲の状態差を確認する。
- 徒歩で140px移動した後は同じ敵手番内で追加移動できず、次の敵手番で徒歩予算が再び最大140pxになる。移動候補シミュレーションの試行距離を実移動量として誤加算せず、確定した移動のみ計上する。
- 代表面以外も71〜99の全対象通常面を複数シードで回し、転移先合法性・回数・クールダウン・攻防の成立を記録する。
- **敵の位置が変わったあとも自機の主攻略・別解が機能するか**を確認する。PR #74で設計された地形をAIの行動で台無しにしない。
- 難易度Easy/Normal/Hardで既存の敵命中率・ダメージ倍率に不要な変更がないことを比較。AI変化による実戦難度の上昇は測定・報告する。
- 同じseedと入力列から、Workerあり・なしで敵の行動種別、着地、射撃、RNG、戦闘結果が一致する。
- セーブからの再開、再挑戦、敵スキップ、プレイヤーのBLINKやテレポート、勝敗確定、最終リレーとの干渉を検証する。
- **安全面のログ：** ステージ、戦闘seed、敵手番、行動種別、移動前後の位置、転移回数、CD、候補数、採用理由、射撃可否、直後の反撃可否を記録し、再現できるようにする。
- 既存の `npm test`、`npm run check:generated`、必要なブラウザテスト、Worker無効時のテストを実施する。未実施は未検証として報告する。

### 7.3 過剰発動を監視する統計

**複数シードで以下を集計する。具体的な許容率は実測バランスから決め、上限そのものは固定値として守る。**

- 戦闘ごとの転移回数（0・1・2）の割合。
- 最初に転移した敵手番の分布（固定の山ができないこと）。
- 最終的な転移先と前後の射線スコアの差。違う足場への分散。
- 徒歩・現在地攻撃・転移の選択率、および「転移せずに済んだ」割合。
- 敵が転移した戦闘での自機の被弾、必要行動数、勝率。転移しない戦闘との比較。
- 転移で自機が反撃不能になったケース、着地失敗、転移の連続発動、固定ターン発動、上限逸脱は**0件が必須**。
