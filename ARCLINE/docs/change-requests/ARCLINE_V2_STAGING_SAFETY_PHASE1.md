- 状態：ユーザー合意に基づく初期実装と検証。GitHubでの配信・公開URL確認・実機は別途記録する。

- 保護対象：本番セーブ、既存URL、GitHub Pagesのmain/root設定、他サイト、100面の現行仕様。

## 1. 決定した運用

STGは本番に影響を与えず、必要な状況から実際に遊んで判断する環境とする。プレイ状態はメモリ内だけに保持する。永続セーブを導入せず、再読み込みまたはタブ終了後は開始条件から作り直す。本番とSTGのセーブを自動同期しない。

STG配信先は `bittrove88/arcline-staging` 専用リポジトリのGitHub Pagesとする。想定URLは `https://bittrove88.github.io/arcline-staging/`。本番のURL・ホスティングは維持する。

本番と同一オリジンであり、ブラウザの保存領域が物理的に隔離される構成ではない。信頼する自分たちのコードを対象とし、保存APIの切替・起動失敗時の停止・ブラウザ検証によって非干渉を確保する。前版の「別オリジン必須」は、今回の小規模な運用に合わせて解除した。

最初は一つのSTGへ、確認したいソースの完全なコミットSHAを指定して手動更新する。PRごとの自動公開は初期対象外。開発途中の試遊と公開前の統合候補確認を、この更新手順で行う。確認結果は表示コミット・成果物ハッシュへ対応させる。

## 3. 最初に実装する範囲

### 起動と状況再現

- 入口は開始ステージN（整数1〜100）の入力と開始ボタン。範囲外入力を拒否する。
- N=1は本番の初回導線を再現。N>1はN面へ進める検証用状態を新規生成し、初期選択をN面、選択可能範囲を1〜Nとする。クリア数の意味は原則N-1であり、N=100を100面クリア済みにしない。
- 初期の難易度は現行通常初期値のNormal。難易度・機体・装備は通常UIで変更する。
- 直接開始時の加入機体・武器解放・章開始在庫・取得台帳・機体補充・物語状態を、現在のデコード／章開始規則と整合する一つの初期化関数で作る。難易度切替後にSTGで選択可能な範囲を失わないよう、未選択モードにも同じ開始規則を適用する。N=1の初回導線は維持する。
- 直接開始用の在庫は検証用の初期値であり、実際に前の全ステージを遊んだ結果ではないと明示する。通常開始後の在庫消費・取得・章またぎはゲーム本来の処理を使う。
- 版、ソースコミット、開始条件の識別子、現在の難易度、一時状態であることを確認できる表示を用意する。再現条件の識別子は保存データではなく、同じ初期化規則を選ぶ情報とする。
- 初期は機体・在庫を自由入力する大規模なデバッグUIを作らない。必要になった状況だけ、版を管理した再現条件として追加する。

### 一時状態と本番保護

- セッション中の攻略・在庫・取得履歴・言語・操作配置・案内状態をメモリだけに保持する。再読み込み／別タブ開始で前のプレイを復元しない。
- STGでは実際のlocalStorage・sessionStorage・IndexedDB・Cookieへゲーム状態を読み書きしない。起動前にこのWindowだけのlocalStorage／sessionStorageをメモリ内の互換オブジェクトへ切り替え、IndexedDB・Cookie・Service Workerへのアクセスを停止する。元のStorage getterやStorage.prototypeを使用・変更せず、他タブのAPIには触れない。切替に失敗したらゲームスクリプトを読み込まない。i18n・操作配置・インストール案内・旧キー削除の直接アクセスも同じメモリ内に収まる。
- 本番SDKのloadData/saveDataを利用しない。SDKや必要な環境設定が無い場合に本番保存へフォールバックする経路を作らない。
- STG用の起動機能は本番URLのクエリだけで有効にできない構成とし、本番成果物へ混入しないことを確認する。
- 本番への自動セーブ取り込み／書き戻し、ユーザーデータ収集、書き出し／取り込み機能は初期対象外。
- STGで本番のPWAインストールを案内しない。初期はSTG用Service Worker・オフライン機能も追加しない。PWA変更を依頼された場合だけ別途検証する。

### 生成と配布

- ゲームの正本は `ARCLINE/game/` と既存の設計正本。現行の生成手順を再利用し、環境差を起動・保存・環境表示・PWA・配信パスへ限定する。
- 配布用スクリプトは、必要なランタイムと素材を許可リストで専用出力先へ組み立てる。他サイト・制作資料・原本ZIP・不要なプロモーション動画を含めない。素材URLを本番へ逃がして読み込む構成にしない。
- 単一のSTG URLは手動更新で内容が変わる。確認したコミット／成果物ハッシュとActionsの記録を残し、必要なら同じ完全SHAを再配信する。URLだけを公開可否判断の根拠にしない。
- 本番は既存GitHub Pagesのまま。STGの配信処理に本番Pagesの公開権限や本番保存の認証情報を与えない。
- 公開予定の統合内容で検証し、通常のPRで本番へ反映する。STG専用ファイルを手作業でコピーして本番化しない。環境差がある最終本番パッケージも対象に応じて確認する。

## 4. GitHub内での配信手順

1. 空の `bittrove88/arcline-staging` を作成し、GitHub連携にアクセスを許可する。GitHub FreeではPublicが必要。Privateの場合はPages対応プランを確認する。
2. 専用リポジトリへREADMEと [配信ワークフロー](../../environments/github-pages/deploy-staging.yml) を配置し、Settings → Pages → SourceをGitHub Actionsにする。本番リポジトリのPages設定は変更しない。
3. 専用リポジトリの `staging-source.json` に、確認したいソースの完全な40桁SHAを指定してコミットする。これは選んだ版の手動更新要求であり、ソースPRへのpushでは自動公開しない。Actionsの「ARCLINE STG manual publish」からSHAを指定して手動実行する方法も使える。
4. ワークフローは公開ソースを指定SHAで取得し、単体・生成物・STGセッションを検証する。`build_staging.py --require-clean` で生成後、ブラウザ検証を通過した成果物だけを専用リポジトリのPagesへ配信する。
5. 公開URLで版・1/50/100面・再読み込み・音声・本番セーブ非干渉を確認する。実機結果は別途記録する。

編集の正本は既存リポジトリのまま。専用リポジトリは配信定義を保持し、ゲームを別途編集しない。ワークフローのGITHUB_TOKENは専用リポジトリの権限を使い、クロスリポジトリ書込み用トークンを新規発行しない。

配布は既存の `build_playables.py` の許可リストと素材ハッシュ検査を再利用する。STG成果物ではHTMLの起動部分と環境用ファイルだけを追加し、ゲーム本体のJS・CSS・画像は元バイト列を維持する。`ARCLINE/game/` と本番用ワークフローには変更を加えない。

Cloudflare等の外部サービス登録・独自ドメイン・本番DNS変更は不要。別オリジンが必要になった段階で、配布物を再利用して移行できる。

- [GitHub Pagesの種類と公開URL](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)
- [GitHub ActionsからのPages公開](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

## 6. 運用開始の受入条件

- N=1/50/100を開始でき、100面は未クリアの最終戦として起動する。範囲外入力は拒否する。
- 難易度変更・機体選択・通常の章進行・持ち物消費をメモリ内で実行できる。変更後の取得物はそのセッション内で本来の規則に従う。
- プレイ後の再読み込み／別タブでは攻略記録を復元せず、同じ初期条件から再現できる。
- 起動前にブラウザのStorage APIとSDK保存APIを監視し、起動・難易度変更・言語変更・操作配置変更・ステージ遷移でゲーム側の永続保存アクセスが無い。通信も確認し、本番SDK保存へ接続しない。
- 本番とSTGを同じブラウザで使い、本番の既存攻略・設定の値が変わらない。実際のユーザー記録を収集せず、検証用プロファイルとテストデータで確認する。
- 画像・BGM・SFX・映画・Workerが専用成果物内の参照先から読み込める。404や旧版混在がなく、表示コミットが対象候補と一致する。
- 本番URLからSTG用の任意ステージ起動を有効にできない。本番セーブの形式・キー・互換性と通常起動を保持する。
- 既存の `npm test`・`npm run check:generated` と変更対象に必要なブラウザ／配布検証が成功する。実機は別に結果を記録し、未確認を成功扱いしない。
- 初期は固定した完全SHAを手動配信し、STGの更新で本番や他サイトを配信し直さない。

# ARCLINE v2 STG安全性 第1段階の変更指示書

- 変更ID：ARV2-BASE-001
- 状態：実装準備PoC。本番未反映
- 変更禁止：ゲーム本体、公開設定、本番セーブ、既存公開URL、他サイト

## 目的
将来の同一ドメイン別パス /ARCLINE-staging/ で、本番公開前のプレイ確認を行う。共通ゲーム本体を二重実装せず、STGは開始ステージの数値入力（1〜100）とゲーム開始だけを追加する。入力NはN面から開始し、1〜N面のステージ選択を可能にする。難易度・機体・装備は通常のゲームUIで操作する。STGの進行状態は一時メモリのみ。

## 第1段階の実装範囲
1. ステージング更新候補のPagesサイト全体と、現在公開中の承認済みPages成果物をファイルハッシュで比較する。
2. /ARCLINE-staging/ 以外のパスが変更・削除・追加されれば、公開を禁止する。STG本編入口がなければ禁止する。シンボリックリンクを禁止する。
3. 変更の単体テストを読み取り専用のActionsで実施する。Pages公開権限は持たせない。
4. 本番ゲームと現在のPages公開方式は変更しない。

## 次の工程で必要な検証
- 同一オリジンの保存領域：本番の既存セーブ・設定をSTGが読み書き・削除しないことを、ブラウザのアクセス監視と変更前後の保存値照合で検証する。
- STG N=1/50/100、難易度変更、ステージ遷移、加入・章持ち物・最終戦の初期状態を検証する。
- 共通ゲーム本体、資産、公開URL、PWA、セーブ、全100面、他サイトへの影響を検証する。
- Pages公開方式変更は、権限・並行公開・完全スナップショット・復旧をPoCで検証後に別PRで実施する。
- 変更ID・目的・ファイル差分・依存関係・検証・承認をPRで管理し、承認済み変更だけのリリース候補を再検証して本番へ昇格する。
- 本番反映前の全ゲートPASSと明示的な承認を必須とする。
