## 1. 更新前に確認すること

1. 最新のユーザー依頼と実装の許可範囲を確認する。「文書のみ」ではゲーム本体を変更しない。
2. [\`AGENTS.md\`](../AGENTS.md)、本ルール、必要な変更指示書の**全文**を読む。
3. \`game/runtime.json\`、\`game/README.md\`、実際のコード、画像、JSON、既存テストを調査し、現行動作と将来要件を分ける。
4. 変更対象と依存関係、既存データへの影響、公開対象のパスを列挙する。
5. 本番への大規模変更には作業ブランチと復旧元コミットを用意する。

## 2. 絶対に守る互換性

- 既存のセーブデータと進行状況、難易度、解放キャラクター、武器、スキル、ストーリー閲覧を無断で初期化しない。
- \`https://bittrove88.github.io/ARCLINE/\` と \`https://bittrove88.github.io/ARCLINE/game/dist/\` の既存公開入口を維持する。
- 戦闘ロジック、100面、ストーリー、原画は依頼された範囲外で変更しない。
- 最新の射線表示はEasy全軌道・Normal半分・Hard発射方向のみ。敵の照準誤差倍率も難易度で異なる。ステージ別敵ダメージ倍率は難易度間で共通。その他のHP・物理・攻撃回数・移動AIは維持。
- 章内で拾った補助武器・スキルは10面ごとの章ボス撃破まで残数を引き継ぐ。同じ章の別の面を選んでも残数を保持し、別の章の選択にはその章の開始規則を適用する。練習扱いには戻さない。
- 仲間選択・紹介では原画を優先し、Canvas代替と重複させない。原画読み込み成功時に親の画像領域まで隠さない。

## 3. 編集元と生成物

- \`game/dist/\` が存在しても、そこだけの直接修正で済ませず、生成元、\`game/runtime.json\`、\`game/README.md\` を確認する。
- 元データから生成されるファイルは、可能な限り正式ビルドコマンドで更新する。
- CSS・JavaScript・画像・JSON・翻訳・manifest・Service Workerの関連参照を一貫して更新する。
- iPhone SafariやAndroid Chromeで旧キャッシュが残らないよう、必要なバージョンやキャッシュ識別子を更新する。
- ファイルパスは大文字・小文字を含めて整合させる。

## 4. ディレクトリ整理

- まず現状構造と参照関係を記録する。重複・未使用・不整合など実際の問題がある場合だけ整理する。
- 移動が必要な場合、HTML、JS、CSS、JSON、ビルド、GitHub Actions、PWA、アセットローダー、ドキュメントリンクをまとめて更新する。
- 構造変更は機能修正とできる限り独立させ、テストとロールバック手段を確保する。
- \`game/src/\` のような存在しない構造を設ける場合は、生成・公開の工程が確定してから移行する。

## 5. 実装チェック

以下は選択肢であり、毎回すべてを実施する一覧ではない。今回の修正と直接の依存先に合わせて選ぶ。選択した確認が成功したら終了し、新しい変更・失敗・具体的な懸念が生じた場合に計画を見直す。

- JavaScript構文、JSON形式、HTML/CSS/JS参照パス
- 画像・音声・キャラクター原画・シネマティックの存在と表示
- セーブデータの旧形式読み込み・進行再開
- 戦闘の照準・発射・弾道・敵AI・ステージ進行
- 仲間加入、編成切り替え、原画と代替Canvasの切り替え
- 章の持ち物・補助武器・練習用武器の動作と説明
- iOS、Android、PCの画面表示、回転、セーフエリア、タッチ／マウス操作
- インストール案内とPWA起動状態
- 更新した日本語・英語文言の整合性
- 公開URLとキャッシュ

修正対象を選択するコマンド例（名前は今回の変更に合わせる）：

    cd ARCLINE
    node game/tools/test.cjs browser battle-turn-continuity-browser --list
    node game/tools/test.cjs browser battle-turn-continuity-browser --skip-aac-probe --fail-fast
    npm test -- attack-motion

全件実行や生成物・配布物の確認が必要な場合は、その根拠を計画へ記載する。詳しいCLIとCI計画の形式は [検証運用](VERIFICATION.md) を参照する。

依存ライブラリや実機が使えずテストを実行できない場合は、未実施項目と理由を記録する。未実施を「成功」と記載しない。

## 6. Git・公開

1. 目的の分かるコミット（\`feat:\`、\`fix:\`、\`refactor:\`、\`docs:\` 等）を作成する。
2. 大きな変更は作業ブランチからPull Requestでマージする。
3. GitHub ActionsとGitHub Pagesの状態を確認する。
4. **コミット済み ≠ ビルド成功 ≠ デプロイ成功 ≠ 公開URLでの確認済み ≠ 実機確認済み** と区別する。
5. デプロイ競合時は進行中のワークフローを調べ、原因を確認してから再実行・復旧する。無条件にキャンセルしない。
6. 本番で問題があればセーブの互換性を守りつつ復旧する。
7. 実施した変更、ファイル、コミット、テスト結果、公開状態、未確認事項を報告する。

**文書のみの更新では、ゲームのUI動作確認や端末テストを実施済みと主張しない。** ただし本番ブランチへのドキュメント反映とCI結果は別途確認する。

## 7. 仕様書・変更要求の運用

- 新しい変更指示書は \`docs/change-requests/ARCLINE_CHANGE_REQUEST_vX.Y.Z.md\` に全文を配置する。
- 現行の有効版への入口を \`AGENTS.md\` と \`README.md\` に置き、**仕様書の版数はゲームの公開バージョンとは別**に管理する。
- 新版で旧版を上書き消去せず、履歴として残してもよい。常に最新の有効版が一意に分かるようにする。
- 個別要求は \`AR-01\` のようなIDで管理し、実装状況は **未着手／実装中／検証中／完了** と検証根拠を分ける。
- 全21章のような長い指示書は、要求表だけでなく共通制約・受け入れテスト・完了条件まで読む。
- \`CODEX_HANDOFF.md\`、\`CODEX_START_PROMPT.md\` など過去時点の引き継ぎは履歴資料として参照し、現在のコードや現行指示書より優先しない。
